# ADR-003 · 无头规则复用与事务存储

状态：部分裁决（2026-11-15）。单机世界采用“快照内联事务”，不引入嵌入式数据库；多写者、金融级规模与部署形态仍待 P0-R3/P0-R6 与 M3 验证。日期：2026-11-14。

## 当前裁决

M3-03 的提交完整性问题已由现有单写者存储解决：`FarmState` 的候选在一次提交中包含资源变更、幂等命令结果（有界 64 条）与事件序号，`FarmStore` 仍以临时件、校验回读、备份和原子重命名写入同一份快照。崩溃恢复因此不需要第二份日志，也不会出现“资源已写、命令结果未写”的单边状态。验证见 [M3-03 记录](../milestones/M3/RECORD-03-commit-recovery.md)。

暂不引入 SQLite 或类似数据库，原因是当前只有一个逻辑写入者、单机文件规模远低于 `FarmStore` 的 512 KiB 上限，且 Godot 绑定、许可证与双平台二进制会增加维护面。出现以下任一需求时重新评估：多写者并发事务、跨进程查询、账本需要超过有界窗口的完整审计、或世界规模稳定超过单文件校验边界。

## 问题与方向

当前 FarmStore 使用 JSON、临时文件与备份，适合现有单机边界。多人交易和银行需要将资源、命令结果与事件序号一起提交。单纯增加更多 JSON 文件可能形成中断后的单边资产变化。

优先复用 Godot 无头规则，验证传递依赖和资源占用后再决定是否抽出其他语言；避免为未来服务器立即重写玩法核心。世界先采用单逻辑写入者，网络请求串行进入规则提交边界。

## 存储候选

小型自建世界优先实验嵌入式事务数据库；具体库、Godot 绑定、许可证和目标平台二进制需核验，当前不声明已采用 SQLite 或任何插件。备选是现有快照加可恢复日志，但必须证明一次提交完整包含状态与命令结果，否则不用于金融。

Nakama 等完整后端只在身份、社交和部署收益超过服务依赖成本时评估。无论采用何种服务，业务账本与房间备份要能导出，不把供应商私有对象作为唯一世界格式。

## 接口与恢复

一次业务事务写入资源变更、事件与幂等结果；确认成功后才能通知客户端已成交。崩溃恢复读取最后完整提交，未完成事务不产生部分结果。快照包含最后事件序号，重放从其后开始；导出先形成一致视图。

选型试验包含提交前/中/后中断、重复命令、备份恢复、长事件尾部和导出期间写入。比较正确性、部署体积、恢复耗时和维护成本。未通过前保留现有单机实现，不将候选数据库塞入正式工程。
