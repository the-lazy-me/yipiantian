# ADR-016 · 规则商人流动性：一次性库存授予与滚动同 id 双边报价

- 状态：采纳（2026-11-15），M7-07 实现完成
- 关联：[M7-07 记录](../milestones/M7/RECORD-08-merchant-liquidity.md)、[ADR-011](ADR-011-market-orders.md)、[ADR-012](ADR-012-matching-settlement.md)、[ADR-014](ADR-014-double-entry-ledger.md)、[M7-06 记录](../milestones/M7/RECORD-06-market-panel.md)

## 背景

M7-02 让规则商人以一次性 600 COIN 预算进入订单簿，但商人没有商品。M7-03 的撮合因此只有玩家互相对手；M7-06 的市场面板能开户、挂单，单机玩家却永远无法与商人完成一笔真实交易。M7-05 的实验也确认：没有商人库存时，玩家卖出没有对手盘，买入也只能等另一个玩家。

需要在不新增第二套钱包、不改变农场格式、不引入随机或系统时钟的前提下，让商人在单机成为稳定对手盘，并且让“商人的货从哪里来”能从快照追溯。

## 决定

### 1. 开市即做一次性商品授予

- `market_open_merchant` 在原有 600 COIN 预算之外，向 `market.merchant.goods` 的六种商品各加 20，共 120。
- 授予写入显式字段 `market.merchant.granted = {good: int}`，每种商品记录 20。它是发行证据，不是第二个库存：商品的唯一余额仍是 `merchant.goods`。
- 开市命令仍是幂等的：同一命令 id 回放不重复授予，另一个命令 id 在商人已开市时返回 `already_opened`，`granted`、库存、现金和订单行都不变。
- 旧市场没有 `granted` 时按全 0 读入，恢复为六个 0 的规范字段；旧市场若商人已开市，不会补发授予（它本来就不存在这笔历史发行）。

### 2. 固定价差：买 base−1，卖 base+1

- 价格只取 `EconomyCatalog.base_price(good)`：买单 `max(1, base − 1)`，卖单 `base + 1`。不读商人现金、库存或成交历史，也不随时间漂移。
- 每种商品一条买单、一条卖单，数量固定 4。买单从商人现金托管，卖单从商人库存托管；托管仍复用现有订单行 `reserved`，商品在卖单开出时即离开 `merchant.goods`，因此不可能被第二张卖单或物流再次使用。
- `quote()` 公开视图返回同一组 bid/ask 和由商人可用现金/库存计算的容量，不新增报价表。

### 3. 滚动报价：稳定 id、原地重开

- 订单 id 固定为 `merchant_bid_<good>`、`merchant_ask_<good>`，`owner = @merchant`。
- 每次 `Market.match(data, now)` 在撮合前做一次确定性维护：某侧报价缺失、已关闭或已到期时，只要商人还有足够现金（买）或库存（卖），就用**同一个订单行**重新开放，刷新 `sequence`、价格、数量、到期、托管状态；绝不新增该侧的第二行。
- 到期但尚未被 `expire` 扫到的行先按现有释放规则退回现金/商品，再重开；两种扫描顺序得到同一结果。
- 商人现金或库存不足以支撑固定 4 单位时，该侧停止补充；另一侧成交回笼现金/库存后，下一次扫描用同一 id 恢复。
- 整个维护只依赖传入的 `now_utc` 和当前数据：无随机数、无系统时钟、无外部服务。相同快照与时间产生相同订单行和序号。

### 4. 成交沿用现有 @merchant 路径

- 买单成交把商品写入 `merchant.goods`，现金从买单托管支付；卖单成交把货款计入 `merchant.cash`，商品从卖单托管交付。费用仍由卖方承担并销毁。
- `_goods_for`／`_ensure_goods` 的商人分支就是现有 `merchant.goods`；不新增商品钱包，也不把商人商品写进任何玩家口袋。
- 商人报价行与玩家订单使用同一张 256 行订单表。稳定 id 让六个商品的两侧永远只占 12 行；玩家不能使用 `merchant_bid_*`／`merchant_ask_*` 作为自己的订单 id。

### 5. 守恒口径

- 现金：`total_cash == issued` 不变；商人现金、买单托管和玩家账户仍是三个现金权威，费用只销毁。
- 商品：`产出 + merchant.granted = 口袋 + 商人库存 + 卖单托管 + 在途 + 已消耗`。授予是一次性产出项，旧市场该项为 0，因此既有场景的公式只需补上授予，不放宽其它断言。
- 每笔商人买单托管、释放、成交与整次维护都写现有 `economy.ledger` 分录；授予商品不改变现金，因此不写现金分录。

### 6. 存档与校验

- 全部新状态仍在 `economy.market.merchant` 内，不新增农场顶层键；农场格式仍为 27，`_valid_snapshot`、`valid_cell_snapshot` 与 `V27Importer.KNOWN_FARM_KEYS` 不变。
- `Market.valid` 严格要求：`granted` 存在时恰好六种商品且为非负安全整数；旧文档缺该字段时补零。商人报价行 id 只允许 `@merchant` 所有，且前缀行总数不超过 12。

## 为什么不是另一侧

- **不给商人第二套余额或库存**：现有账户、`merchant.cash`、订单 `reserved` 和 `merchant.goods` 已经能表达托管与成交。第二套表会让每条现金/商品路径都要维护两处，并无法说明哪一处权威。
- **不在开市时生成无限库存**：固定价差且库存无限会产生无底对手盘，玩家可以无限卖出入。一次性 20/商品让商人真正会耗尽，并让“恢复”来自另一侧成交。
- **不做动态调价或 AI 做市**：本切片只证明单机存在稳定对手盘。动态价差需要需求估计、风险与长期世界调参，属于后续裁决。
- **不用每次扫描新建订单行**：新行会迅速撞上 256 行上限，破坏订单表与存档形状；稳定 id 原地重开同时解决行数、幂等和追溯。
- **不把授予记成玩家产出或共享库存**：授予是商人这一规则主体的发行，必须能从 `granted` 追溯，不能伪装成某块地的收成。

## 后果

- `market_state.gd` 新增商品授予、固定价差、滚动报价维护、商人报价 id 保护与 `granted` 校验；`open_merchant` 在开市时立即生成 12 条报价。
- 现有商人视角的 quote 由旧的 4/5 base 与 5/4 加成改为 base±1；引用该数值的旧夹具同步到新价格。
- 单机市场首次具备可成交的双边流动性，但价格仍是固定实验值。
- 未覆盖：动态调价、做市 AI、Windows/CI 实机、长寿命世界的耗尽/恢复统计、按市场地点拆分流动性、网络权限。

## 复审触发条件

出现以下任一情况时重开本裁决：固定价差被证明让玩家存在稳定套利；商人长期耗尽且没有恢复路径；订单表或日志上限在真实时长内成为约束；需要按地点或玩家区分流动性；或网络世界要求商人报价由权威侧显式命令而非扫描维护。
